# 微博舆情管理系统 设计文档

- 日期：2026-10-29
- 状态：已实现 MVP（2026-10-30），实现范围与差距见 [`11_系统架构设计.md`](11_系统架构设计.md)

## 1. 背景与目标

团队需要持续监控微博上整体舆情情况，看清声量和情感的走势，及时发现负面事件，并人工标注一批样本，用来校准和评估自动情感判断。

### 1.1 目标

1. 从微博采集四类数据：关键词搜索结果、命中帖子的评论与转发、指定账号的发帖、热搜榜。
2. 采集结果存在本地数据库，可以在前端查询和浏览。
3. 前端展示舆情趋势：声量、情感占比、负面突增、热搜命中。
4. 支持对样本做情感标注（正面 / 中性 / 负面），支持多人协作，并记录是谁标注的。
5. 自动情感打分引擎可以仅支持本地模型，并用人工标注评估两者的准确率。

### 1.2 非目标（本期不做）

- 分布式爬虫、代理池
- 微博以外的平台
- 告警推送（飞书、邮件等），本期只在页面上标红
- 情感以外的标注维度（相关性、议题分类、风险处置工单）
- 公网部署与多租户

### 1.3 使用场景与规模

- 使用者是小团队（个位数到十几人），部署在内网，单机 Docker Compose。
- 预估数据量：几十个关键词加几十个监控账号，每天新增帖子和评论在万级。

## 2. 总体架构

```
┌────────────── Docker Compose（内网单机） ──────────────┐
│                                                         │
│  crawler（采集进程）           api（FastAPI）            │
│   ├ 调度器 APScheduler          ├ 舆情查询 / 趋势聚合    │
│   ├ 关键词搜索                  ├ 标注 / 用户登录        │
│   ├ 评论·转发                   └ 采集配置 / Cookie 管理  │
│   ├ 指定账号时间线                    ▲                  │
│   ├ 热搜榜                            │                  │
│   └ sentiment worker            web（Vue3 + ECharts）    │
│        │                                                 │
│        ▼                                                 │
│     PostgreSQL                                           │
└─────────────────────────────────────────────────────────┘
```

| 组件 | 技术选型 | 职责 |
|---|---|---|
| crawler | Python 3.11、httpx、APScheduler、Playwright（只用于扫码登录和兜底抓取） | 定时采集，原始数据入库 |
| sentiment worker | Python，跟 crawler 同一个进程，量大时可拆成独立容器 | 从待打分队列取文本，调用当前引擎打分 |
| api | FastAPI、SQLAlchemy | 查询、聚合、标注、配置、鉴权 |
| web | Vue3、Element Plus、ECharts | 前端四个页面 |
| db | PostgreSQL 16 | 全部业务数据和任务队列 |

不引入 Redis 或 MQ。任务队列和待打分队列都用 PG 表实现，取任务用 `SELECT … FOR UPDATE SKIP LOCKED`。

## 3. 采集模块

### 3.1 采集方式

主路径是 m.weibo.cn 移动端 JSON 接口，请求带上已登录微博账号的 Cookie。Playwright 只做两件事：

1. 扫码登录，拿 Cookie。
2. 某类接口连续失败（默认 5 次）时，改抓 s.weibo.com 网页做兜底。

### 3.2 采集任务

| 任务 | 接口 | 默认频率 | 增量策略 | 去重键 |
|---|---|---|---|---|
| 关键词搜索 | `/api/container/getIndex?containerid=100103type=1%26q={kw}` | 每个关键词 15 分钟一次 | 按时间倒序翻页，遇到已入库的 mid 或翻满 50 页就停 | mid |
| 评论 | `/comments/hotflow?id={mid}&mid={mid}` | 新帖入库后立即抓一次，之后 24 小时内每 2 小时补抓一次 | 用 max_id 翻页 | 评论 id |
| 转发 | `/api/statuses/repostTimeline?id={mid}` | 只抓转发数 ≥ 阈值（默认 20）的帖子，频率同评论 | 翻页直到遇到已入库的数据 | 转发 mid |
| 指定账号 | `/api/container/getIndex?containerid=107603{uid}` | 每个账号 30 分钟一次 | 遇到已入库的 mid 就停 | mid |
| 热搜榜 | `https://weibo.com/ajax/side/hotSearch`（不用登录） | 10 分钟一次 | 每次存整榜快照 | 快照时间 + 词条 |

- 热搜词条命中任一关键词时，把该词条临时加入关键词搜索，有效期 24 小时，同时在趋势看板标出来。
- 帖子的互动数（转评赞）每次被重新抓到时更新，同时在 `post_metric` 里留一份快照，用来看传播曲线。

### 3.3 账号池与限速

- 可以录入多个微博账号，请求在账号之间轮换。单个账号最快每 2.5 秒发 1 个请求，并带随机抖动。
- 遇到 418 或 403 时，该账号冷却 30 分钟。连续 3 次冷却后，账号标记为「异常」，停止使用。
- 判定 Cookie 失效的条件：接口返回登录跳转，或者 `ok != 1` 且带有登录提示。失效后账号标记为「需重新登录」，设置页标红。
- 扫码登录流程：管理员在设置页点「扫码登录」，后端用 Playwright 打开登录页，把二维码截图推给前端，扫码成功后保存 Cookie。

### 3.4 合规

- 只采集公开内容，不采集私信和非公开主页。
- 作者信息只存 uid、昵称、粉丝数、认证状态。
- 系统只在内网访问，需要登录才能使用。
- 原始 JSON 默认保留 90 天，可以配置，到期由定时任务清理。

## 4. 数据模型

```
keyword(id, word, enabled, is_temp, expire_at, created_by, created_at)
watch_account(id, uid, nickname, enabled, created_at)
weibo_cookie(id, account_name, cookie_enc, status[ok|cooling|need_login|abnormal],
             cooling_until, last_used_at, fail_count)

author(uid PK, nickname, followers, verified, updated_at)
post(mid PK, text, author_uid, created_at, reposts, comments, likes,
     is_repost, root_mid, raw jsonb, fetched_at)
post_source(mid, source_type[keyword|account|hotsearch], source_value, first_seen_at)
                                   -- 一条帖子可能有多个来源
post_metric(mid, ts, reposts, comments, likes)
comment(id PK, mid, text, author_uid, created_at, likes, reply_to, raw jsonb)
repost(mid PK, root_mid, text, author_uid, created_at, raw jsonb)
hot_search_snapshot(ts, rank, word, heat, label, matched_keyword_id NULL)

-- 情感：文本统一用 (text_type, text_id) 引用，text_type 取 post / comment / repost
sentiment_queue(text_type, text_id, enqueued_at, locked_at)
sentiment_auto(text_type, text_id, engine, engine_version, label, score, created_at)
              -- 每个 engine 一行，方便对比
sentiment_label(text_type, text_id, user_id, label, created_at, updated_at)
              -- 一人一条，可以修改

app_user(id, username, password_hash, role[admin|annotator], enabled)
crawl_log(id, task_type, target, cookie_id, started_at, finished_at,
          status, items, error_code, error_msg)
setting(key PK, value jsonb)   -- 当前情感引擎、阈值等
```

- `label` 的取值：`pos`、`neu`、`neg`。
- **最终情感**规则（做成视图 `v_sentiment_final`）：
  1. 有人工标注的取多数票。票数打平时取最新的一条。
  2. 没有人工标注的，取 `setting.active_engine` 对应的自动结果。
  3. 两者都没有的，记为未打分，趋势图里单独显示。
- Cookie 用环境变量里的密钥做对称加密后再存储。

## 5. 情感引擎

### 5.1 接口

```python
class SentimentEngine(Protocol):
    name: str
    version: str
    def classify(self, texts: list[str]) -> list[tuple[str, float]]: ...
        # 返回 (label, score)，label 取 pos / neu / neg，score 取 0~1
```

### 5.2 实现

| 引擎 | 说明 | 批量 | 失败处理 |
|---|---|---|---|
| `llm` | 调用 Claude Haiku 或国产大模型（可配置 base_url 和模型名）。prompt 要求只输出 JSON 标签和置信度，并附 10 条 few-shot 示例，示例从人工标注里挑 | 每批 20 条 | 最多重试 3 次，指数退避；解析失败的单条回到队列，3 次后标为失败 |
| `local` | 中文 RoBERTa 情感模型，CPU 推理。用标注数据微调后的权重放在挂载目录里 | 每批 64 条 | 异常时整批回到队列 |

- 新文本入库时进入 `sentiment_queue`，worker 只用当前启用的引擎打分。
- 设置页可以切换当前引擎，也可以对某段时间的历史数据用指定引擎重跑。重跑的结果写入新的 `sentiment_auto` 行，旧结果保留。
- **评估**：以有人工标注的文本为基准，算每个引擎的准确率、各类别 F1 和混淆矩阵。本地引擎和 LLM 的一致率达到预设水平（例如负面 F1 ≥ 0.8）后，可以考虑切换。
- **导出**：人工标注可以导出成 jsonl（`{"text":..., "label":...}`），用来微调本地模型。

## 6. 后端 API（摘要）

| 方法与路径 | 说明 |
|---|---|
| `POST /auth/login` | 登录，返回 JWT |
| `GET /posts` | 舆情列表。筛选参数：keyword、source、time_from、time_to、sentiment、min_interactions、q（正文模糊匹配）；支持分页和排序 |
| `GET /posts/{mid}` | 帖子详情，包括评论、转发和互动曲线 |
| `GET /trend/volume` | 声量时间序列。参数：粒度（小时或天）、关键词，可按关键词拆分 |
| `GET /trend/sentiment` | 情感占比时间序列 |
| `GET /trend/alerts` | 负面突增时段 |
| `GET /trend/top-negative` | 高互动负面帖 Top N |
| `GET /hotsearch` | 热搜快照和命中记录 |
| `GET /label/next` | 取下一条待标注样本。参数：抽样策略、筛选条件 |
| `PUT /label/{text_type}/{text_id}` | 提交或修改自己的标注 |
| `GET /label/stats` | 个人和整体进度、标注员之间的一致率 |
| `GET /eval` | 各情感引擎的评估指标 |
| `GET /export/labels` | 导出标注 jsonl |
| `CRUD /config/keywords`、`/config/accounts`、`/config/users` | 配置管理，仅管理员可用 |
| `POST /config/cookies/qrcode`、`GET /config/cookies` | 扫码登录与 Cookie 状态 |
| `POST /config/engine`、`POST /sentiment/rerun` | 切换引擎、历史数据重跑 |
| `GET /crawl/logs` | 采集日志 |

权限：标注员可以使用查询、趋势和标注三类接口；配置类接口只有管理员可用。

## 7. 前端页面

### 7.1 舆情列表

- 左侧是筛选栏，右侧是帖子卡片流。卡片显示作者、时间、正文、转评赞数、来源标签和最终情感。
- 情感标签可以直接点选修改，修改即生成当前用户的一条人工标注。
- 点开卡片进入详情：显示评论列表（每条也带情感标签）、转发列表、互动随时间变化的曲线。

### 7.2 趋势看板

- 顶部筛选：时间范围（默认近 7 天）、关键词（可多选）、粒度。
- 图表：
  1. 声量折线，可按关键词拆成多条线
  2. 情感占比堆叠面积图，加一条负面占比折线
  3. 负面突增标记
  4. 热搜命中时间轴
  5. 高互动负面帖 Top 10
- **负面突增规则**：某小时的负面条数超过前 7 天同一时段均值的 3 倍，且绝对值不少于 10 条，即判为突增。阈值可在设置页修改。

### 7.3 标注工作台

- 抽样策略有三种：随机、低置信度优先（score < 0.6）、两个引擎结果不一致优先。还可以限定时间、关键词和文本类型。
- 每次显示一条文本，同时显示它所属帖子的上下文（如果是评论，显示原帖）。快捷键 1/2/3 分别对应正面、中性、负面，S 跳过，← 回到上一条修改。
- 自己已标注过的样本不会再次出现在自己的队列里。
- 页面一角显示今日已标注数、累计数，以及和其他标注员的一致率。

### 7.4 设置（仅管理员）

关键词管理、监控账号管理、微博账号池（状态、扫码登录、冷却情况）、情感引擎切换与重跑、评估页、系统用户管理、采集日志。

## 8. 错误处理

| 场景 | 处理 |
|---|---|
| 接口 418/403 | 账号冷却，换下一个账号继续；全部账号都不可用时任务跳过本轮，写入 crawl_log |
| Cookie 失效 | 账号标记为需重新登录，设置页和顶部栏标红 |
| 接口结构变化或解析失败 | 原始响应写入 crawl_log；同类任务连续 5 次失败后切到 Playwright 兜底 |
| 情感引擎调用失败 | 重试后放回队列，不阻塞采集 |
| 数据库写入冲突 | 用 upsert 按主键幂等写入 |
| 调度任务重入 | 同一任务同时只跑一个实例（APScheduler 的 max_instances=1） |

## 9. 测试

- **解析单测**：录制各接口真实返回的 JSON 作为固定样本，测解析、去重和增量停止条件。
- **限速与账号池单测**：模拟 418 和登录失效，验证冷却和切换逻辑。
- **情感引擎**：接口契约测试；LLM 引擎用 mock 测输出解析和失败重试。
- **API 测试**：pytest 加测试库，覆盖筛选、聚合口径、最终情感视图和权限。
- **冒烟测试**：docker compose 起全套服务，回放录制数据，验证「采集 → 打分 → 看板出数 → 标注 → 最终情感变化」整条链路。

## 10. 部署

- 一个 `docker-compose.yml`，包含 db、crawler、api、web 四个服务（web 由 nginx 托管静态文件，同时反代 api）。
- PG 数据目录挂载到宿主机，并配一个每天 pg_dump 备份的定时任务。
- 首次启动时自动建表，并创建默认管理员。默认管理员的初始密码随机生成，打印在日志里，首次登录必须修改。
